# PythonProjectTransporterSeven

Рабочий проект конвейера с семью камерами, YOLO-моделями, defect rules, Conveyor и двухосевым распределителем.

## Установка Windows

```bat

```

Модели должны находиться в существующих путях `weights/...`, указанных в `vision/model_config.py`. При загрузке проверяются не только пути, но и точный список классов модели. Несовпадение классов останавливает запуск до начала инспекции.

## Production-голосование по трём кадрам

После каждого подтверждённого шага Conveyor остаётся неподвижным, а система последовательно получает три свежих синхронных набора всех семи камер. Каждый набор независимо проходит соответствующие YOLO-модели и defect rules. Для каждого правила отдельно применяется строгое большинство:

```text
2 или 3 срабатывания из 3 → правило сработало
2 или 3 нормы из 3        → правило в норме
```

После этого штатная логика `Part` формирует общий маршрут `ГОДНО / БРАК / НА ОЧИСТКУ`. Голосование выполняется по правилам, а не по готовому маршруту и не путём объединения segmentation masks разных кадров.

`part_presence` также голосует 2 из 3. Если два кадра подтверждают пустой лоток, результат остаётся нейтральным, `Part` и архив детали не создаются. Если два кадра подтверждают наличие детали, все три результата моделей проходят INPUT defect rules, чтобы каждое правило имело три полноценных голоса.

Все три прогона обязательны. Ошибка камеры, модели, неполный набор правил или иной невалидный прогон не заменяется результатом `ГОДНО`: production-цикл переходит в `FAULT`. В правой панели возле правила показывается итог вида `НОРМА · 3/3` или `СРАБОТАЛО · 2/3`. Для каждой пары camera/model три запуска сворачиваются в одну строку `3 ПРОГОНА` со средним временем и тремя количествами detections, чтобы не перегружать HMI. В `meta.json` архива детали записывается `inspection_consensus` с голосами INPUT и SPIDER/TOP.

Кнопка `АНАЛИЗ КАДРА` в UI также получает три свежих изображения, но только с выбранной камеры. Модели и локальные правила этой камеры выполняются трижды и голосуют 2 из 3; совместный `part_presence` для одной INPUT-камеры помечается как невыполненный. `analyze_saved_images.py` не менялся и анализирует явно выбранные сохранённые файлы. Время model inference на production-шаг и на UI-анализ нужно проверить на рабочем ПК с реальными `.pt`.

## Этапы шага и разделение камер

Шаг линии разбит на явные фазы, у каждой ровно один владелец камер.
Переход между фазами — единственное место, где владелец меняется.

```text
MOTION     лента едет             камеры у live-просмотра
SETTLE     лента встала           камеры у live-просмотра, гасим вибрацию
CAPTURE    лента неподвижна       камеры только у инспекции
ANALYSIS   модели и правила       камеры не читаются
REVIEW     пауза на просмотр      лента стоит, кадры с разметкой на экране
PUBLISH    результат на экран     камеры не читаются
```

Первый шаг после пуска особый (`INITIAL_INSPECTION`): лента не двигается.
Если деталь уже стояла под входными камерами на момент пуска, она
инспектируется на шаге 0 и попадает в учёт, а не уезжает непроверенной.
Движение начинается со второго шага, поэтому позиции детали по линии —
вход 0, контроль +4, сортировка +7 — отсчитываются от фактических
перемещений ленты.

После `ANALYSIS` линия держит паузу `REVIEW_SECONDS` (по умолчанию 5 с,
задаётся необязательным полем `review_time` в `calibration.json`,
диапазон 0..30 с) с обратным отсчётом в строке фазы: оператор успевает
отсмотреть работу нейросетей, пока кадры со статичной разметкой и итоги
правил остаются на экране. Пауза прерывается остановкой или выходом из
программы; в тестах она отключается параметром `review_seconds=0`.

Порядок фаз задан таблицей переходов в `core/step_stages.py`. Вызов не по
порядку поднимает `StageSequenceError`, поэтому «снять кадр для правил во
время движения» невозможно не по договорённости, а по построению.

`SETTLE` существует отдельно от `CAPTURE`: контроллер подтверждает
остановку по счётчику шагов, а механика в этот момент ещё качается. Кадр,
снятый сразу после подтверждения, может быть смазан. Длительность задаётся
полем `settle_time` в `calibration.json` (по умолчанию 0.15 с, диапазон
0..5 с). Поле необязательное — старые файлы калибровки остаются валидными.

Каждая смена фазы печатается в консоль вместе с длительностью предыдущей:

```text
[STAGE] MOTION -> SETTLE (предыдущая фаза 0.30 с)
[STAGE] SETTLE -> CAPTURE (предыдущая фаза 0.30 с)
```

Для отладки шаг можно растянуть: поле `stage_trace_time` в
`calibration.json` задаёт паузу перед каждой фазой (по умолчанию 0,
диапазон 0..5 с). Пауза берётся, когда лента уже остановлена или ещё не
тронулась, поэтому на физику линии и на результат правил она не влияет —
только замедляет шаг, чтобы фазы было видно по отдельности. В production
значение должно оставаться нулевым.

Текущая фаза доступна в `/api/status` как `live.stage`.

Пока лента едет, оператор видит поток: выбранная камера обновляется с
частотой `LIVE_TARGET_FPS`, остальные шесть — одним пакетом раз в
`LIVE_AUX_BATCH_INTERVAL`. Разметка правил в этот момент снимается: она
построена по статичному кадру и на движущемся изображении указывала бы
мимо детали.

На `CAPTURE` камеры переходят к инспекции, и все три прогона моделей и
defect rules выполняются по кадрам неподвижной детали. Владение держится
до начала следующего движения, поэтому результат голосования остаётся на
экране вместе с кадрами, по которым он посчитан.

Передачу камер выполняет `LiveCaptureGate` в `core/live_preview.py`.
Пауза не просто выставляет флаг, а дожидается завершения уже начатых
live-чтений: инспекция никогда не читает камеру параллельно с фоновым
потоком. Если live-поток не освободил камеры за отведённое время, шаг
завершается ошибкой, а не выполняется на конкурентном доступе. При любой
ошибке шага фазы сбрасываются в `IDLE`, а камеры возвращаются просмотру.

Живой просмотр работает и в `JOG`, и в `RUNNING`/`STOPPING`. Индикатор
над камерой показывает текущий режим: `ПОТОК · N FPS` во время движения,
`СТОП-КАДР · ПРАВИЛА` на статических фазах и `АНАЛИЗ` при разборе трёх
кадров выбранной камеры.

Семь камер открываются волнами по три, а не все сразу: одновременный
старт перегружает USB-контроллер, часть камер остаётся без изохронной
полосы и отдаёт `read returned no frame` на исправном железе. Внутри
волны камеры стартуют параллельно, поэтому preflight не суммируется.
Preflight каждой ждёт стабилизации экспозиции до 5 секунд, и каждая
камера получает две попытки с перебором backend-ов (`CAP_DSHOW`, затем
`CAP_MSMF` на Windows): разовый отказ резервирования полосы лечится
пересозданием `VideoCapture`, а не увеличением таймаута. Ошибки
собираются по всем камерам сразу, чтобы оператор видел полный список
проблем, а не первую. В тексте ошибки указываются число пустых чтений и
реально согласованный драйвером формат.

MJPG при этом не просто запрашивается, а **доказывается фактическим
FOURCC**: драйверы принимают формат в разном порядке set() (часть —
только до смены разрешения, часть — только после) и подтверждают set()
даже при молчаливом отказе. Откат `MJPG -> YUY2` поднимает поток одной
камеры примерно с 25 до 440 Мбит/с и лишает полосы все остальные,
поэтому оба порядка перебираются до тех пор, пока `get(CAP_PROP_FOURCC)`
не вернёт MJPG. Откат — громкое предупреждение, а с
`CAMERA_REQUIRE_MJPG=1` — ошибка открытия.

Тайминги старта настраиваются переменными окружения
(`CAMERA_OPEN_CONCURRENCY`, `CAMERA_PREFLIGHT_TIMEOUT`,
`CAMERA_OPEN_ATTEMPTS`, `CAMERA_OPEN_RETRY_DELAY`, `CAMERA_OPEN_TIMEOUT`,
`CAMERA_BACKENDS`). Проверки near-black и разрешения они не ослабляют.
Разбор конкретного отказа — `preflight_checks\11_RUN_CAMERA_DIAGNOSTIC.bat`
(он же показывает согласованный кодек каждой камеры и явно ругается на
любой формат не-MJPG).

На слабом USB-контроллере (все семь камер на одном корневом хабе)
полосу пополам делит `CAMERA_FPS=15`: для статичной инспекции 15 кадров
достаточно, а изохронных слотов хватает всем камерам.

Чтение кадров идёт через постоянный пул потоков: истёкший таймаут не
бросает исключение поверх ещё работающих воркеров, а латчит менеджер.
Но прежде чем латчить, захват пытается **восстановить упавший поток на
месте**: при просадке питания/полосы USB-драйвер прекращает отдавать
кадры, оставляя устройство формально открытым, и лечится это только
пересозданием `VideoCapture`. Роль пересоздаётся под своим lock с
pre­flight-ом нового handle до замены (ни одна другая роль не затрагивается,
production-цикл не падает из-за одной просадки), и только если
`CAMERA_RECOVERY_ATTEMPTS` (по умолчанию 2) не помогли — менеджер
фиксирует ошибку, как раньше. Бюджет восстановления на попытку —
`CAMERA_RECOVERY_PREFLIGHT` секунд.

## Проверка сохранённых изображений

Отдельная утилита `analyze_saved_images.py` запускает production-модели и применимые правила на сохранённых изображениях без камер, COM-порта и движения оборудования.

Интерактивный режим запускается указанием обычной папки. Имена изображений могут быть произвольными:

```powershell
.\.venv\Scripts\python.exe analyze_saved_images.py C:\inspection_images
```

В окне программы:

1. выберите изображение из списка;
2. назначьте ему класс камеры;
3. при необходимости назначьте классы другим изображениям комплекта;
4. нажмите `ENTER` для запуска моделей и применимых правил;
5. переключайте `RAW / ПРАВИЛА` клавишей `TAB`;
6. нажмите `СОХРАНИТЬ ОТЧЁТ`, если результат нужно записать на диск.

Если хотя бы одно правило сработало, утилита автоматически открывает режим `ПРАВИЛА`, чтобы красная геометрия или явная причина отказа сразу были видны. Для просмотра исходных детекций после этого нажмите `TAB` или кнопку `RAW`. Для парных правил статус в правой панели рассчитывается локально по выбранной камере: дефект `INPUT_RIGHT` больше не помечает исправный кадр `INPUT_LEFT` как локально ошибочный. При браке на другой назначенной камере выводится отдельное пояснение.

Доступны классы:

```text
КЛАСС 1/6 · ВХОД СЛЕВА / СПРАВА
КЛАСС 2/7 · КОНТРОЛЬ СЛЕВА / СПРАВА
КЛАСС 3/5 · ВНУТРЕННИЙ / НАРУЖНЫЙ ВИД
КЛАСС 4   · ВИД СВЕРХУ
```

Правая панель показывает по текущему изображению:

- разрешение и яркость;
- все фактически запущенные модели;
- время каждой модели;
- количество объектов;
- статистику по каждому классу объектов;
- confidence min/max/среднее;
- все отдельные детекции, bbox, число точек mask, площадь mask в px² и модель-источник;
- отдельный блок подбора порога площади для `long_omission` / `short_omission`;
- выполненные правила и их результаты;
- правила, которые не выполнены из-за отсутствующих связанных камер;
- общую категорию и список дефектов.

Пакетный режим остаётся доступен через `--batch`. Для него используются имена `TOP.jpg`, `INPUT_LEFT.jpg`, префиксы вида `part_001_TOP.jpg`, подпапки, JSON manifest или явные `--image ROLE=PATH`.

```powershell

```

Сводка автоматически записывается в:


Связи правил теперь следующие:

```text

```

В обоих contact rules существующие проверки собственной геометрии и вписываемого прямоугольника сохранены. Связь с omission используется только как дополнительная проверка общего наклона ряда.

### Геометрия двух коротких контактов

`contacts_short` на `SPIDER_IN/SPIDER_OUT` сначала применяет минимальную площадь `400 px²` ко всем detections, включая случай исходного количества ровно два. Затем выбирается лучшая пара valid segmentation masks; лишние detections показываются серым пунктиром. BBox fallback запрещён.

Для пары проверяются `Δtop`, `Δbottom` и `Δheight`. Допуск равен `median_contact_height × level_deviation_ratio`: для `SPIDER_IN` установлен коэффициент `0.45`, для `SPIDER_OUT` — `0.35`. В каждую mask вписывается rectangle `25.2×9.6 px`; размер задаётся непосредственно в пикселях порогами `spider_contacts_short_inscribed_rect_width_px` / `spider_contacts_short_inscribed_rect_height_px`, физический масштаб больше не вычисляется.

Renderer показывает без чисел и текстовых пояснений: два contact contours, два rectangles, верхнюю и нижнюю соединяющие линии с коридорами допуска, два вертикальных height-сегмента, линию `omission-short` и два перпендикуляра. Sample points, чёрные подложки и подписи расстояний удалены. Невозможное построение использует единые короткие сообщения `CONTACTS N/2`, `NO CONTACT MASK`, `NO OMISSION`.

Справа выводятся общие дельты и допуск, rectangle, omission tilt, а также top/bottom/height, rectangle result и distance до omission для каждого из двух контактов.

### Наклон коротких контактов относительно omission

Все найденные mask `omission-short` объединяются. Над диапазоном двух контактов из верхнего контура берутся до 31 точки, после чего строится устойчивая линия Theil–Sen. Для верхней точки каждого контакта рассчитывается перпендикулярное расстояние до этой линии:

```text
tilt_ratio = abs(distance_A - distance_B) / median_contact_height
```

Брак:

```text
tilt_ratio > spider_contacts_short_omission_tilt_ratio_max
```

Стартовый предел отдельно для `SPIDER_IN` и `SPIDER_OUT` равен `0.20`:

```json
"SPIDER_IN": {
    "spider_contacts_short_omission_tilt_ratio_max": 0.20
},
"SPIDER_OUT": {
    "spider_contacts_short_omission_tilt_ratio_max": 0.20
}
```

Если `omission-short` отсутствует или линию невозможно построить, проверка бракует деталь fail closed, сохраняет доступную геометрию пары и выводит короткое `NO OMISSION`. В режиме `ПРАВИЛА` отображаются линия omission и два перпендикуляра без sample points, индексов и числовых подписей.

### Геометрия пяти длинных контактов

`contacts_long` на `SPIDER_LEFT/SPIDER_RIGHT` выбирает наиболее ровный ряд из пяти `contacts-long`; лишние detections показываются серым пунктиром и не участвуют в решении. Для всех пяти обязательны valid segmentation masks. Неверное количество или отсутствующая mask вызывают fail closed без bbox fallback.

По верхним и нижним границам пяти mask строятся две линии. Допустимое отклонение каждой границы равно `median_contact_height × 0.35`. В каждую mask вписывается прямоугольник `11.5×8.6 px` алгоритмом «центр → ближайшее допустимое положение»; размер задаётся непосредственно в пикселях порогами `spider_contacts_long_inscribed_rect_width_px` / `spider_contacts_long_inscribed_rect_height_px`, физический масштаб больше не вычисляется.

Renderer не содержит заливок, индексов, чисел и текстовых сообщений. Он показывает контуры пяти mask, пять эталонных прямоугольников, верхнюю и нижнюю линии с коридорами допуска, линию `omission-long` и пять перпендикуляров. Верхняя и нижняя линии имеют разные цвета; violated geometry становится красной. Отсутствующая omission reference показывается красным крестом через диапазон ряда.

Справа для каждого из пяти контактов выводятся отклонения верх/низ относительно допуска, результат rectangle и расстояние до omission. Общая строка содержит размер rectangle и итоговый omission tilt ratio.

### Наклон пяти длинных контактов относительно omission

Все mask `omission-long` также объединяются, а верхняя линия строится тем же устойчивым методом. Для каждого из пяти контактов вычисляется перпендикулярное расстояние `d1..d5`. По этим расстояниям вдоль ряда строится второй тренд Theil–Sen. Проверяется не единичный выброс, а общий наклон всего ряда:

```text
long_tilt_ratio = abs(predicted_distance_right - predicted_distance_left)
                  / median_contact_height
```

Порог отдельно для двух камер:

```json
"SPIDER_LEFT": {
    "spider_contacts_long_omission_tilt_ratio_max": 0.20
},
"SPIDER_RIGHT": {
    "spider_contacts_long_omission_tilt_ratio_max": 0.20
}
```

Это закрывает случай, когда все пять контактов лежат на идеальной прямой и проверка собственного ряда проходит, но весь ряд наклонён относительно `omission-long`. Отсутствующая опорная линия также вызывает fail closed. В `ПРАВИЛА` рисуются линия omission и пять перпендикулярных расстояний без sample points, индексов и числовых подписей.

## Контрольная полоса omission

Для `long_omission` и `short_omission` используется одна общая реализация геометрии, но в DecisionEngine остаются только два производственных правила с этими именами. Отдельного третьего правила `omission_boundary` нет. В каждом правиле проверяется только одна основная mask — самая большая по площади. Дополнительные маленькие детекции остаются в `RAW` и не влияют на решение.

По верхнему контуру основной mask строится устойчивая линия Theil–Sen. Контрольные линии заканчиваются точно по ширине основной mask; дополнительного продления по краям нет. Единственная нижняя линия строится перпендикулярным отступом от верхней:

```text
верхняя линия
→ allowed_thickness_px
→ окончательная limit line
```

Пиксели основной mask ниже limit line разбиваются на связные компоненты с 8-связностью. Компоненты размером меньше `excess_component_min_px` считаются цифровым шумом и не рисуются. Если хотя бы одна компонента достигла порога — деталь бракуется. При стартовом значении 3 одиночный пиксель и связная пара игнорируются, но узкий вертикальный хвост из трёх и более пикселей остаётся дефектом. Дополнительной жёлтой линии, safety margin, фильтра по ширине или соседним столбцам нет. В вычислении остаётся только непараметрический epsilon `0.01 px`, защищающий от float-ошибки вида `20.004` на математической границе 20 px.

Параметры задаются отдельно для каждой камеры:

```json
"SPIDER_LEFT": {
    "spider_long_omission_allowed_thickness_px": 20.0,
    "spider_long_omission_excess_component_min_px": 3,
    "spider_long_omission_top_line_max_residual_px": 3.0
},
"SPIDER_IN": {
    "spider_short_omission_allowed_thickness_px": 20.0,
    "spider_short_omission_excess_component_min_px": 3,
    "spider_short_omission_top_line_max_residual_px": 3.0
}
```

`SPIDER_RIGHT` и `SPIDER_OUT` имеют собственные независимые значения. Если mask отсутствует, повреждена или верхнюю линию нельзя устойчиво построить, правило срабатывает fail closed.

Общий renderer применяется одинаково к `long_omission` и `short_omission`. В `ПРАВИЛА` остаются только контур основной mask без заливки, голубая верхняя линия, зелёная limit line и красная заливка подтверждённых excess-компонент. Полный контур valid mask не становится красным из-за локального excess. Sample points, чёрные подложки линий, надпись `BELOW LIMIT LINE` и другие числовые подписи удалены. Шумовые компоненты 1–2 px не рисуются.

Дополнительные маленькие omission detections остаются исключительно в `RAW`: они не рисуются и не выводятся в статистику. При отсутствии valid measurement renderer показывает только короткую подпись `NO VALID OMISSION` без технической причины на кадре.

Справа и в offline calibration остаются только согласованные параметры: допустимая толщина, минимальная компонента, фактический/допустимый residual верхней линии, самая большая компонента, подтверждённые excess-пиксели и максимальная глубина выхода. Raw noise, ignored components, X-диапазон и число столбцов из операторской статистики удалены.

## Размеры вписываемых прямоугольников

Алгоритм поиска положения сохранён: сначала прямоугольник проверяется по центру mask, затем ищется ближайшее к центру допустимое положение.

```text
SPIDER_LEFT/RIGHT contacts-long: width=11.5 px, height=8.6 px
SPIDER_IN/OUT flatness_short:    width=25.2 px, height=9.6 px
TOP contacts L/R:                width=28 px, height=35 px
TOP contacts T/B:                width=30 px, height=28 px
TOP platform, внутренний:        width=260 px, height=120 px
TOP platform, область заплыва:   строится по контактам (без фиксированного размера)
```

Ни одна камера больше не использует физический масштаб (`px/mm`, `px/um`). Размеры задаются непосредственно в пикселях:

```json
"TOP": {
    "top_contacts_side_rect_width_px": 28,
    "top_contacts_side_rect_height_px": 35,
    "top_contacts_edge_rect_width_px": 30,
    "top_contacts_edge_rect_height_px": 28,
    "top_platform_inscribed_rect_width_px": 260,
    "top_platform_inscribed_rect_height_px": 120,
    "top_platform_overlap_excess_component_min_px": 3,
    "top_platform_overlap_contact_min_confidence": 0.3,
    "top_platform_overlap_contact_inner_ratio": 0.5,
    "top_platform_overlap_margin_px": 0,
    "top_platform_overlap_expand_x_ratio": 1.0,
    "top_platform_overlap_expand_y_ratio": 1.0
}
```

`top_contacts` использует axis-aligned bbox основной platform mask и формирует группы `5L+5R+2T+2B`. Если valid contact masks больше четырнадцати, внутри каждой стороны выбирается требуемое количество detections с наиболее одинаковым расстоянием до стороны bbox; при равном разбросе приоритет имеет больший confidence. Лишние detections показываются серым пунктиром.

Для каждой группы строится параллельная reference-линия по медианному отступу и перпендикуляры от центров контактов к соответствующей стороне platform bbox. Допустимый разброс равен `median contact width/height × 0.4`. Равномерность шага вдоль стороны не проверяется. В contacts L/R вписываются rectangles `28×35 px`, в T/B — `30×28 px`.

Renderer показывает platform bbox, четыре reference-линии, четырнадцать перпендикуляров, contours и rectangles без заливок, индексов и чисел. Нарушенный distance или rectangle становится красным. Невозможные построения используют короткие сообщения `CONTACTS N/14`, `NO CONTACT MASK`, `NO PLATFORM`, `NO PLATFORM BBOX`, `LAYOUT ...`. Справа выводятся четыре group summary и distance/deviation/rectangle для каждого из четырнадцати контактов.

Для `TOP platform` контакты не требуются. Используется только самая большая valid platform mask; дополнительные detections остаются исключительно в `RAW`. По ориентации `minAreaRect` строится rectangle `260×120 px`: сначала по центру bbox mask, затем в ближайшем положении, где каждый пиксель rectangle находится внутри segmentation mask. Если допустимого положения нет — `БРАК`.

Renderer показывает нейтральный contour platform, rectangle, исходный центр bbox и фактический центр rectangle. При смещении центры соединяются линией; при невписываемости красным становится rectangle, а не вся mask. Невозможность построить reference обозначается `NO PLATFORM` или `NO ORIENTATION`. Справа остаются только размер, angle, centered/shifted/not fitted и shift distance; coordinates centers и extras не публикуются.

`top_contacts` остаётся самостоятельным и не изменяет решение по заплыву платформы. Отдельный файл `rule_top_platform_overlap.py` и правило `platform_contacts_overlap` сохранены, но старая проверка фактического пересечения `platform/contact` внутри него удалена.

Теперь правило строит прямоугольную область **по контактам**. Контакты TOP с confidence не ниже `top_platform_overlap_contact_min_confidence` группируются по сторонам платформы `L/R/T/B` в системе координат, повёрнутой на угол platform mask.

Платформа всегда считается стоящей вертикально. `minAreaRect` возвращает угол *длинной* оси mask, поэтому у вертикально стоящей детали он равен ~90°, и рабочая система координат легла бы набок: стороны `L/R` и `T/B` поменялись бы местами, а `expand_x/y_ratio` растягивали бы область поперёк ожидаемого направления. Угол нормализуется в диапазон `[-45°, 45°]`, так что ось X рабочей системы всегда совпадает с горизонталью детали (стороны `L/R`), ось Y — с вертикалью (`T/B`). Реальный физический наклон детали при этом сохраняется. Для каждого контакта берётся опорная координата по `top_platform_overlap_contact_inner_ratio`: `0.5` — центр контакта (значение по умолчанию), `0` — кромка, обращённая к платформе, `1` — внешняя кромка. Медиана опорных координат внутри каждой группы задаёт одну сторону прямоугольника; полученная область дополнительно расширяется наружу на `top_platform_overlap_margin_px` и масштабируется коэффициентами `top_platform_overlap_expand_x_ratio` / `expand_y_ratio`. Затем прямоугольник возвращается в исходную систему координат с тем же углом, что и платформа.

Область строится только по контактам — концентрический fallback вокруг вписанного прямоугольника `260×120 px` удалён вместе с параметрами `top_platform_overlap_boundary_width/height_px`. Если контактов не хватает хотя бы по одному на каждую из сторон `L/R/T/B`, построение невозможно: правило бракует деталь с reason `contact_boundary_not_built` и сообщением `NO CONTACT RECT`.

Если платформа пересекает границы построенного прямоугольника, срабатывает правило пересечения. Пиксели platform mask снаружи границы разбиваются на 8-связные компоненты: компоненты из 1–2 пикселей считаются шумом, связный выход от `top_platform_overlap_excess_component_min_px = 3 px` бракует деталь как заплыв платформы.

Renderer показывает нейтральный contour platform и чистую тонкую пунктирную зелёную `(0, 255, 0)` рамку области. Точки опорных контактов остаются в diagnostics/details, но на оверлее не рисуются, чтобы не закрывать контакты. Вышедшая за границу область выделяется полупрозрачной красной заливкой с красным контуром. Рамка области не меняет цвет при браке, надпись `PLATFORM OVERFLOW` отсутствует. Используются короткие сообщения `NO PLATFORM`, `NO ORIENTATION`, `NO CONTACT RECT`. Справа остаются boundary size, component min, largest component, confirmed pixels и число контактов области; raw/ignored metrics, anchor center и angle не публикуются.

### TOP shells внутри case_central

Правило `sinks` выполняется только при наличии `shells`. Тогда обязательны valid mask каждой shell, ровно одна `case_central`, основная platform mask и тот же согласованный комплект лучших четырнадцати contacts `5L+5R+2T+2B`, который выбирает `top_contacts`. Отдельный threshold confidence для contacts в `sinks` удалён; используется `top_contacts_min_confidence=0.3`.

Проверка выполняется попиксельно:

```text
forbidden = shell
            AND case_central
            AND NOT platform
            AND NOT selected contacts
```

Любой forbidden pixel вызывает `БРАК`. Поэтому shell, частично пересекающая platform/contact, всё равно бракуется, если другая её часть остаётся внутри case_central вне защищённых зон.

Renderer при дефекте показывает contour `case_central`, platform и четырнадцати contacts как reference geometry, нейтральный contour исходной shell и красную заливку только forbidden pixels. Shells без forbidden region остаются только в `RAW`. Невозможные построения используют `NO SHELL MASK`, `CASE CENTRAL N/1`, `NO PLATFORM`, `NO PLATFORM BBOX`, `CONTACTS REF ...`.

Справа для каждой дефектной shell выводятся forbidden pixels и фактические overlaps с case_central, platform и contacts.

### TOP glass → ОЧИСТКА

При наличии `glass` общий context требует valid основную platform mask, тот же согласованный комплект лучших четырнадцати contacts `5L+5R+2T+2B`, ровно четырнадцать valid pins, ровно одну `case`, одну `case_central` и valid masks всех glass. Дополнительный `top_glass_contacts_min_confidence` удалён; используется `top_contacts_min_confidence=0.3`.

Сначала glass проверяется на contacts. Любой contact overlap имеет приоритет `БРАК` и исключает эту glass из CLEANUP rule. Если contacts не пересечены, route `ОЧИСТКА` назначается при любом пикселе glass на platform, union pins или кольце `case-case_central`. Glass вне всех зон остаётся только в `RAW`.

CLEANUP renderer показывает нейтральные contours platform и pins, границы case/central, янтарный contour glass и янтарную заливку только фактического union overlap. Полная glass mask не закрашивается. Справа для каждой glass отдельно выводятся overlap pixels с platform, pins, ring и итоговый cleanup union.

### TOP glass на contacts → БРАК

`glass_on_contacts` использует полный общий glass context. Отсутствие любой обязательной platform/contact/pin/case/central reference приводит к fail closed и маршруту `БРАК`. Для valid context каждая glass проверяется отдельно с каждым из выбранных четырнадцати contacts; любой общий пиксель создаёт отдельную подтверждённую пару `glass/contact`. Glass может сформировать несколько BAD-пар одновременно.

BAD renderer показывает все selected contact contours, янтарный contour glass и красную заливку только фактических contact-overlap pixels. Полная glass mask не закрашивается. Справа каждая пара выводится отдельно: glass index, contact index, overlap pixels и route `БРАК`.

Ошибки общего context используют доступные glass contours и короткие сообщения `NO GLASS MASK`, `NO PLATFORM`, `CONTACTS REF`, `PINS N/14`, `NO PIN MASK`, `CASE N/1`, `CASE CENTRAL N/1`, `INVALID CASE RING` или `EMPTY CASE RING`.

## Организация thresholds.json

Файл сгруппирован по семи камерам: `INPUT_LEFT`, `INPUT_RIGHT`, `SPIDER_LEFT`, `SPIDER_RIGHT`, `SPIDER_IN`, `SPIDER_OUT`, `TOP`. Между секциями оставлены пустые строки; служебные ключи `_comment...` удалены, поэтому в файле находятся только рабочие параметры и `disabled_rules`.

При запуске выполняется проверка схемы:

- отсутствующий обязательный параметр останавливает запуск;
- проверяются диапазоны confidence, размеры, количества и min/max;
- скрытые fallback-параметры из правил сопоставляются со схемой regression-тестом.

Дополнительные (новые) пороги можно добавлять в `thresholds.json` вручную в любом количестве: они подхватываются при запуске, появляются в панели «ПОРОГИ ПРАВИЛ» (группа «Прочие пороги») и свободно редактируются там же. Единственное ограничение — значение должно быть конечным числом. Изменения, сделанные в панели, сохраняются в файл; при работе программы файл также перечитывается автоматически (см. панель «ПОРОГИ ПРАВИЛ» в правой колонке).

Аудит текущей конфигурации: отсутствующих обязательных параметров нет. Ранее неявные `top_glass_case_*` и `top_glass_pin_min_confidence` теперь явно записаны в секции `TOP`; неиспользуемый общий `min_confidence` удалён.

## Запуск только UI

Без камер, моделей, COM и физического движения:

```bat
setup_ui_only.bat
run_ui_only.bat
```

`setup_ui_only.bat` устанавливает только лёгкие UI-зависимости и не устанавливает `ultralytics`/`torch`.

Откроется тот же интерфейс 1280×720 с синтетическими кадрами, fake-деталями, JOG, диагностикой распределителя, camera/model/rule отчётами и кнопками START/STOP. Этот режим предназначен только для доработки и просмотра UI.

## Запуск реальной системы

```bat
run.bat
```

При запуске программа:

1. находит контроллер по ответу статуса `I2`;
2. применяет скорость, ускорение и геометрию Conveyor;
3. открывает и проверяет семь камер 1280×720;
4. блокирует near-black кадры;
5. загружает и прогревает все модели;
6. создаёт inspection pipeline;
7. выполняет физический G28 homing обеих осей распределителя;
8. открывает UI.

Текущая известная аппаратная проблема: `INPUT_RIGHT` выдаёт чёрный кадр. Программа теперь остановит инициализацию на проверке камеры и не начнёт homing, пока камера не будет исправлена.

Если камера не проходит preflight с `read returned no frame`, она открылась, но не отдала кадр. Это чаще нехватка полосы USB, чем поломка: запустите `preflight_checks\11_RUN_CAMERA_DIAGNOSTIC.bat`, чтобы отличить одно от другого.

После открытия камеры прогреваются (`CAMERA_WARMUP_SECONDS`, по умолчанию 2.5 с): первые кадры после простоя тёмные из-за неуспевшей автоэкспозиции, и читать их в инспекцию нельзя. Камера, которая после прогрева не дала ни одного кадра или осталась тёмной, догревается точечно (`CAMERA_RECOVERY_WARMUP_SECONDS`). Если повторное чтение не помогло, поток считается мёртвым и целиком пересоздаётся с preflight-ом нового handle — как и при production-восстановлении (бюджет на роль — `CAMERA_RECOVERY_REOPEN_SECONDS`, по умолчанию 6 с). Старт останавливается с «Камеры не стабилизировались после прогрева», только когда не помогло ни то, ни другое; в тексте ошибки указано, по какой роли и что именно не так (нет кадров / тёмные кадры / поток не пересоздался).

```text
vision/ui/static/js/

  boot.js          splash, boot и готовность UI
  diagnostics.js   камеры, модели, rules и распределитель до START

```

Порядок подключения зафиксирован в `index.html` и проверяется тестом. Возврат к монолитным `app.js`/`style.css` запрещён regression-тестом.

Интерфейс полностью локализован на русский язык и использует единый словарь оператора. Состояния линии: `ГОТОВА К ПУСКУ`, `РАБОТАЕТ`, `ОСТАНОВКА ЛИНИИ`, `ОСТАНОВЛЕНА`, `АВАРИЯ`, `НЕТ СВЯЗИ`. Категории деталей: `ГОДНО`, `БРАК`, `НА ОЧИСТКУ`. Для DIST1 используются положения `ПРОХОД` и `СБРОС`, для DIST2 — каналы `БРАК` и `ОЧИСТКА`. Технические идентификаторы команд и API при этом не изменены.

Тема интерфейса строгая и тёмная: сплошные нейтральные панели, тонкие границы и приглушённый акцент. Цветные градиенты, shimmer и циклические анимации производственной линии отключены. Основная семантика статусов сохранена: зелёный — нормальная работа, красный — авария или брак, жёлтый — переходное состояние или очистка.

Компоновка следует принципам высокопроизводительного промышленного HMI: нейтральный фон, цвет только для состояния и результата, крупный основной кадр, контекстный правый блок и постоянная нижняя панель управления. Используются локальные системные шрифты Windows, поэтому оформление не зависит от доступа в интернет. Статистика собрана в компактную сетку, нормальные состояния осей показаны нейтрально, а красный цвет зарезервирован для аварии и брака.

Визуальные изменения выполняются короткими неповторяющимися переходами: панели плавно сворачиваются и раскрываются, кадры и отчёты мягко заменяются, значения статистики обновляются без резкого мерцания. Маркеры распределителя интерполируются между телеметрическими координатами за 220 мс при опросе 60 мс. Эти переходы не задерживают блокировку кнопок, отправку `G1`, обработку heartbeat или показ аварии. Для системной настройки `prefers-reduced-motion` переходы практически отключаются.

## Фильтр ложного наличия детали на INPUT

Служебное правило `part_presence` использует `flatness` на `INPUT_LEFT` и `INPUT_RIGHT` до запуска остальных входных правил. На каждой камере независимо отбрасывается количество `0..2`, но для подтверждения детали обязательны обе камеры:

```text
INPUT_LEFT  >= 3 И INPUT_RIGHT >= 3 → деталь присутствует
INPUT_LEFT  <= 2 ИЛИ INPUT_RIGHT <= 2 → деталь не обнаружена
```

Например, `INPUT_LEFT=7`, `INPUT_RIGHT=0` считается отсутствием детали. Это согласованная fail-open для пустой ячейки логика: `Part` не создаётся и деталь не отслеживается дальше по линии.

Порог явно записан для каждой камеры:

```json
"INPUT_LEFT": {
    "input_part_presence_false_positive_max_count": 2
},
"INPUT_RIGHT": {
    "input_part_presence_false_positive_max_count": 2
}
```

Все исходные detections остаются видны в `RAW`. По согласованной политике `part_presence` вообще ничего не рисует в `ПРАВИЛА`: ни при отсутствии детали, ни при ложных 1–2 detections, ни при подтверждённом наличии. При отсутствии подтверждения обеих камер справа нейтрально выводится только `ДЕТАЛЬ НЕ ОБНАРУЖЕНА`. Это не дефект, не красное срабатывание и не причина брака; увеличивается `empty_count`, а `Part`, архив детали и остальные INPUT defect rules не создаются.

## Правило положения перекладины INPUT

`window_geometry` для `INPUT_LEFT/INPUT_RIGHT` проверяет семь областей `flatness` на каждой камере. Границы области определяются по mask. Разделяющая точка — нижняя граница горизонтальной перекладины в центральной зоне.

Для каждого окна рассчитываются два абсолютных размера:

```text
T = верх mask → нижний край перекладины, px
B = нижний край перекладины → низ mask, px
```

Отношения и нормализация по полной высоте mask больше не используются. Для `INPUT_LEFT` и `INPUT_RIGHT` в `thresholds.json` заданы независимые диапазоны `top_px_min/max` и `bottom_px_min/max`:

```json
"INPUT_LEFT": {
    "input_window_geometry_top_px_min": 20,
    "input_window_geometry_top_px_max": 40,
    "input_window_geometry_bottom_px_min": 20,
    "input_window_geometry_bottom_px_max": 40
},
"INPUT_RIGHT": {
    "input_window_geometry_top_px_min": 20,
    "input_window_geometry_top_px_max": 40,
    "input_window_geometry_bottom_px_min": 20,
    "input_window_geometry_bottom_px_max": 40
}
```

Актуальные значения `20..40 px` применены отдельно к обеим входным камерам. Любое окно вне допуска бракует деталь.

Renderer `window_geometry` показывает все семь выбранных окон только контурами, без заливки, индексов и текстовых подписей. На каждом окне строятся нижний край перекладины и оба размерных отрезка: `T` имеет голубой цвет, `B` — янтарный; конкретный размер за допуском становится красным, как и контур плохого окна. Числа для всех семи окон выводятся только в правой панели.

Если найдено больше семи detections, выбирается наиболее ровный ряд из семи, а лишние mask показываются серым пунктиром и не участвуют в решении. Если найдено меньше семи, все фактически найденные mask обводятся красным без текстовой плашки; справа выводится `найдено N/7`. При отсутствующей или непригодной segmentation mask рисуются красный bbox/контур и диагональный крест, а справа для соответствующего индекса указывается `нет измерения T/B`.

## Раковины внутри окон INPUT

Правило `window_sinks` проверяет класс `objects` относительно тех же семи `flatness`, которые выбирает `window_geometry`. При количестве больше семи используется тот же наиболее ровный ряд, а лишние window mask не участвуют. Если `objects` отсутствуют, reference windows не требуются и правило возвращает норму.

При наличии хотя бы одной sink detection обязательны segmentation masks самой sink и всех семи выбранных окон; bbox fallback удалён. Недостаточное количество окон, повреждённая window mask или sink mask приводят к fail closed.

Для каждой sink и каждого выбранного окна отдельно рассчитывается:

```text
overlap_px = sink_mask AND window_mask
```

Пара `sink/window` вызывает брак при `overlap_px >= 5`. Пересечения разных sinks и разных окон не суммируются. `objects` вне выбранных окон остаются только в `RAW`, не рисуются в `ПРАВИЛА` и не выводятся в статистику.

Renderer показывает нейтральный контур соответствующего окна, красный контур sink и красную заливку только фактических overlap-пикселей. Полная sink и полное окно не закрашиваются, текстовых подписей на кадре нет. При повреждённой обязательной mask рисуются красный bbox/контур и диагональный крест.

Справа при браке каждая подтверждённая пара выводится отдельно:

```text
раковина #1 → окно #3: overlap 9 px >= 5 px
```

## Проверка перед START

В `IDLE` и после полного `STOPPED` оператор может без движения production-линии:

1. удерживаемыми `←`/`→` поправить положение ленты;
2. проверить четыре положения DIST1/DIST2;
3. просмотреть все семь камер с максимальным FPS выбранной роли;
4. нажать `АНАЛИЗ КАДРА` и проверить модели, голоса 2/3 и локальные правила выбранной камеры.

Общие проверки камер, загрузки моделей и regression rules убраны из правой панели UI и находятся в `preflight_checks/`. При START, RUNNING, STOPPING, занятом JOG, движении распределителя, активном анализе кадра, FAULT или OFFLINE диагностические действия блокируются.

## Калибратор камер

Если при запуске отсутствует `camera_mapping.json`, `run.bat` автоматически открывает отдельный оконный мастер `КАЛИБРОВКА КАМЕР` до инициализации COM, Conveyor и распределителя. Консольный вопрос `y/n` удалён.

Мастер выполнен в той же профессиональной тёмной HMI-стилистике, что и основное приложение, но открывается обычным окном. Он последовательно:

1. изолированно проверяет Camera ID `0..9` с повторными открытиями: каждая камера проверяется наедине с шиной, без конкуренции за полосу USB с уже найденными соседями, — поэтому число исправных камер не «плавает» от запуска к запуску;
2. принимает только камеры с валидным кадром `1280×720`, не near-black;
3. одновременно открывает семь проверенных камер и оставляет их открытыми, поэтому переключение в мастере не выполняет повторный медленный запуск DirectShow, а комплект гарантированно откроется и в production;
4. по очереди назначает роли `INPUT_LEFT`, `INPUT_RIGHT`, `SPIDER_LEFT`, `SPIDER_RIGHT`, `SPIDER_IN`, `SPIDER_OUT`, `TOP`;
5. не позволяет повторно использовать один Camera ID;
6. разрешает назначение только после появления живого preview;
7. перед сохранением показывает итоговый комплект `7/7`.

Частичный JSON не записывается. После подтверждения полный mapping валидируется и атомарно сохраняется через временный файл. Затем окно калибратора закрывается, а основное приложение продолжает запуск автоматически. Если исправных камер меньше семи, мастер показывает оформленную ошибку, `camera_mapping.json` не создаётся и запуск основной программы блокируется. При этом мастер различает «камера не отвечает даже изолированно» (подключение/питание/драйвер) и «камеры исправны поодиночке, но не вместе» (нехватка пропускной способности USB-контроллера), а кнопка `ПОВТОРИТЬ ПОИСК` перезапускает сканирование после исправления оборудования без перезапуска окна. Тайминги сканирования настраиваются переменными окружения `CAMERA_SCAN_OPEN_ATTEMPTS`, `CAMERA_SCAN_RETRY_DELAY`, `CAMERA_SCAN_PROBE_ATTEMPTS`.

Существующий, но повреждённый JSON автоматически не перезаписывается: это остаётся startup-ошибкой. Для ручной повторной калибровки используется:

```bat
run_camera_calibration.bat
```

Процедура не открывает COM-порт и не отправляет команды движения. Подробная инструкция находится в `preflight_checks/10_CAMERA_CALIBRATION_RU.md`.

## Калибровка распределителя

Если позиции DIST1/DIST2 не соответствуют механике, не подбирать числа в UI. В `Distributor` больше нет скрытых fallback-порогов 300/200: обе координаты обязательны и загружаются только из проверенного `calibration.json`. Перед G28 Python отправляет для каждой оси `G31 S0`, `G32 S<maximum>`, `G33 S1` и проверяет `limMin/limMax` через I11. После homing проверяются `POS=0`, `HOMED=1`, `LIM=1`. Текущие значения DIST1 OPEN и DIST2 CLEANUP равны 340. Для изменения использовать отдельный guarded-скрипт:

```bat
run_distributor_calibration.bat
```

Подробная процедура находится в `preflight_checks/09_DISTRIBUTOR_CALIBRATION_RU.md`. Скрипт отдельно калибрует DIST1 OPEN и DIST2 CLEANUP, создаёт candidate JSON и применяет его только после точной фразы `APPLY DISTRIBUTOR CALIBRATION` с резервной копией старого файла.

## Интерфейс линии и распределителя

Под главным окном камеры находится путь детали из восьми позиций. Под лентой конвейера стоит статичная сетка из восьми графических ячеек с постоянными обозначениями `1 · ВХОД`, `5 · КОНТРОЛЬ`, `8 · СОРТИРОВКА`; промежуточные позиции обозначены числами 2, 3, 4, 6 и 7. Сами детали показаны отдельными маркерами поверх сетки: внутри маркера только короткий ID вида `#1`, категория подсвечивается цветом рамки. На каждом шаге маркеры плавно скользят ровно на одну ячейку вправо, повторяя движение конвейера; сошедшая с линии деталь съезжает за последнюю ячейку и исчезает. Никаких эффектов внутри самих ячеек нет — анимирован лишь сдвиг маркеров, синхронный с реальным временем проезда ленты. Текущая фаза шага показывается компактной подписью справа над линией; телеметрия Conveyor словами не выводится.

Панель `АНАЛИЗ ТЕКУЩЕГО КАДРА` в рабочем цикле привязана к выбранной оператором камере: при каждом переключении камеры (клик по превью или клавиши 1–7) сводка сразу меняется. Для `INPUT_LEFT`/`INPUT_RIGHT` показывается последний результат стадии ВХОД, для остальных пяти камер — результат стадии КОНТРОЛЬ +4 с указанием номера детали, которой он принадлежит. После каждого шага линия держит паузу просмотра (по умолчанию 5 с) с обратным отсчётом, чтобы оператор успел отсмотреть работу нейросетей.

В правой панели находятся DIST1 и DIST2. Маркеры перемещаются по фактически прочитанным координатам осей и остаются полностью внутри шкалы в крайних положениях. Операторский диапазон начинается с нулевого положения: временные отрицательные координаты firmware при поиске нуля не показываются, но стартовый G28 всё равно обязан подтвердить реальный `POS=0`. После этого обе оси работают по абсолютным координатам. Операторские кнопки DIST1 `ПРОХОД` и `СБРОС` соответствуют внутренним командам `DIST1_HOME` и `DIST1_OPEN`; кнопки DIST2 `БРАК` и `ОЧИСТКА` соответствуют `DIST2_BAD` и `DIST2_CLEANUP`. Поле `ТЕКУЩИЙ КАНАЛ` показывает фактическое последнее положение DIST2 и больше не сбрасывается в прочерк. Во время работы линии кнопки блокируются, но фактические координаты и движение распределителя остаются видимыми. Непосредственно перед пуском программа автоматически возвращает DIST1 в положение `ПРОХОД`, а DIST2 — в канал `БРАК`.

Статистика рабочего цикла постоянно видна в `IDLE`, `RUNNING`, `STOPPING` и `STOPPED`, включая период до первого пуска и после полной остановки. Анализ текущего кадра располагается сразу под статистикой, раскрывается на полную высоту содержимого и не имеет собственного внутреннего ползунка. При нехватке высоты прокручивается вся правая колонка как единая область.

Кнопки ручного позиционирования DIST1/DIST2 доступны и раскрыты только в `IDLE/STOPPED`. С момента ПУСК они плавно сворачиваются и не появляются до состояния полной остановки `STOPPED`; координаты, шкалы и текущие положения распределителей при этом остаются видимыми.

## LIVE и анализ выбранного кадра

В `IDLE/STOPPED`, в том числе во время удержания ручного хода, выбранная LIVE-камера имеет отдельный поток захвата с целевой частотой 30 кадров/с. Дополнительные шесть камер читаются вторым независимым потоком каждые 0,20 секунды и больше не останавливают чтение основной камеры. Для каждой VideoCapture используется отдельный lock: одна камера не читается конкурентно, но разные камеры могут работать параллельно. При открытии запрашиваются MJPG, 1280×720, 30 FPS и минимальный буфер драйвера. Основной кадр передаётся последовательными завершёнными HTTP-запросами, а миниатюры обновляются только при изменении версии конкретной камеры.

Плашка `ПОТОК · <частота> КАДР/С` является только индикатором и не реагирует на наведение или нажатие. Переключатель `RAW / ПРАВИЛА` скрыт в обычном режиме ожидания. Он показывается только во время анализа выбранного кадра и во время основного производственного цикла. В режиме `RAW` отображаются все сырые детекции моделей. В режиме `ПРАВИЛА` отображается только геометрия применимых правил.

Панели `RULES` и `STATS` больше не встраиваются непосредственно в изображение камеры. На кадре остаются только контуры, измерительные линии, цвет результата и короткие подписи конкретной ошибки. Для всех rules действует единый контракт: если обязательное построение невозможно, renderer показывает доступную геометрию и одну короткую ASCII-подпись (`WINDOWS 4/7`, `NO T/B #3`, `NO CONTACT MASK #2`, `NO SCALE`, `NO OMISSION`); подробная причина остаётся справа. Текст не заменяет геометрию, когда построение возможно.

DebugOverlay выполняет композицию drawings перед рендером. Основную reference geometry рисует только правило-владелец: `window_geometry` владеет window contours, `top_platform` — platform contour, `top_contacts` — contact contours, `sinks` — case_central. Зависимые `window_sinks`, `platform_overlap`, `glass` и `glass_on_contacts` повторно эти contours не рисуют, но сохраняют fallback reference при отдельном запуске. Одинаковые construction-error сообщения объединяются, разные автоматически размещаются отдельными строками, и все error labels рисуются последним слоем.

Кнопка `АНАЛИЗ КАДРА` приостанавливает поток и последовательно получает три свежих изображения только с выбранной камеры. Каждый кадр независимо проходит назначенные модели и локальные правила; итог каждого правила принимается большинством 2 из 3. Другие камеры не захватываются. Для INPUT служебный `part_presence`, которому одновременно нужны `INPUT_LEFT` и `INPUT_RIGHT`, явно помечается как невыполненный. Правый блок показывает среднее время модели, три количества detections и голоса правил. Во время анализа обычная статистика, распределитель и ручное управление временно скрыты. После `ВЕРНУТЬ ПОТОК` отчёт очищается, а обычные панели восстанавливаются.

## JOG

Панель ручного управления лентой отображается только в состояниях `IDLE` и `STOPPED`: до пуска и после полной остановки линии. В `RUNNING` и `STOPPING` панель полностью скрыта. Доступны только две кнопки `←` и `→`. После первого heartbeat запускается длинный непрерывный сегмент `jog_hold_steps` из `calibration.json`; при длительном удержании сегмент автоматически продолжается. При отпускании кнопки, уходе указателя, потере фокуса, скрытии страницы или пропаже heartbeat немедленно отправляется `G1`. После остановки восстанавливаются `normal_steps` и `G6 S2`.

## Доступность команд

- До первого корректного `/api/status` все motion/control кнопки disabled.
- `IDLE/STOPPED`: доступны START, JOG и диагностика распределителя, если нет занятой операции.
- Во время удержания JOG: START, EXIT и диагностика распределителя заблокированы.
- Во время диагностики распределителя: START, EXIT и JOG заблокированы.
- `RUNNING`: доступен только штатный STOP и EXIT.
- `STOPPING`: START/STOP/JOG/диагностика недоступны; EXIT становится повторным force-exit.
- `FAULT`: доступен только FORCE EXIT, причина FAULT отображается поверх камеры и в процессе.
- `OFFLINE`: все команды заблокированы; удерживаемый JOG прекращается по heartbeat timeout.

Для физического запуска независимый E-stop должен быть доступен оператору.
