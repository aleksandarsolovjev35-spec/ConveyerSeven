# Аудит порогов правил и русских подписей

**Дата аудита:** 5 августа 2026

Текущая таблица отражает набор значений, подтверждённый оператором и
загруженный в `thresholds.json`; перед записью он прошёл валидацию схемы.

## Что проверено автоматически

- `thresholds.json` содержит **96 привязок параметров к камерам** и **61
  уникальный параметр**.
- Каждый параметр, который читают defect rules, обязателен в конфигурации:
  скрытых значений по умолчанию для рабочего контура нет.
- Для каждой роли набор полей, который отдаёт `GET /api/thresholds`, теперь
  точно совпадает с набором параметров этой роли в `thresholds.json`.
- Для всех 61 параметров есть русская подпись и русское пояснение. Пояснение
  доступно оператору при наведении на название поля и приходит в API в поле
  `description`.
- Диапазоны и шаги числовых полей сверены с валидацией на сервере. В
  частности, UI больше не предлагает ноль там, где алгоритм требует
  положительное целое число.

Это проверка **согласованности кода, файла конфигурации и HMI**. Она не может
сама подтвердить, что численные значения подходят конкретной реальной детали:
для этого нужны эталонные годные/бракованные кадры и прогон
`analyze_saved_images.py` или проверка на стенде.

## Что исправлено в HMI

### Уточнены переводы и единицы

| Было неоднозначно | Теперь показано в интерфейсе |
|---|---|
| «Верх/низ зоны окон» | **T до перекладины** и **B после перекладины**: видно, какую именно часть маски измеряет порог. |
| «Заплавы» для `objects`/`shells` | **Раковины**: «Раковины в окнах» и «Раковины корпуса». |
| «Мин. размер лишнего фрагмента, px» | **Мин. число пикселей в компоненте избытка/заплыва**. Правило считает 8-связную компоненту, а не её длину. |
| «Доля внутренней зоны контакта» | **Положение опорной точки контакта (0…1)**. `0` — кромка к платформе, `0.5` — центр, `1` — внешняя кромка. |
| «Макс. наклон, %» | **Доля высоты**. В значении `0.20` нет неявного перевода в 20: UI показывает ровно коэффициент, с которым работает правило. |
| Неспецифичные «уверенность контактов/платформы» | Подписи теперь указывают контекст: для границы, для раковин, для стекла, для контактов сверху и т. п. |

### Исправлены ограничения ввода

- `input_window_sinks_overlap_min_px` — только целое число **от 1**. Ноль
  означал бы дефект даже при нулевом пересечении масок.
- Количество длинных контактов — минимум **2**, так как для линии и тренда
  нужны не менее двух точек.
- Число коротких контактов показано, но заблокировано на **2**: алгоритм
  проверяет именно пару.
- Число TOP-контактов показано, но заблокировано на **14**: топология
  правила в коде фиксирована как `5L + 5R + 2T + 2B`; другое число раньше
  выглядело редактируемым, но не могло корректно изменить раскладку.
- Для коэффициентов и `margin` убраны произвольные верхние потолки HTML
  (например, прежний `max=1`, `max=10`, `±500`), которых нет в серверной
  схеме.

## Общие пороги между правилами

Некоторые поля находятся в карточке правила-владельца, но используются ещё
и другими правилами. Это явно написано в подсказках:

- уверенность окон INPUT используется и в **«Наличии детали»**;
- уверенность `omission-long`/`omission-short` используется также в проверке
  наклона соответствующих контактов;
- уверенность TOP-контактов используется также в правилах **раковин корпуса**
  и **стекла**.

## Рекомендация перед изменением чисел

1. Сохранить резервную копию `thresholds.json`.
2. На остановленной линии изменить **один** параметр.
3. Проверить набор годных и подтверждённо бракованных кадров в
   `analyze_saved_images.py --batch`.
4. Сверить три прогона в панели «Анализ кадра» и только затем переносить
   настройку в production.

Так не смешиваются две разные задачи: исправность/понятность интерфейса и
подбор физически правильного допуска для конкретной камеры и изделия.
