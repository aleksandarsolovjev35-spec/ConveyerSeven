# Анализ UI «Анализ кадра» — причины проблем с раскладкой

Разбирал панель `#frame-analysis-panel` (кнопка «АНАЛИЗ КАДРА») в правой колонке HMI.
Панель построена на flex, но в CSS есть конфликт, который ломает задуманную высоту
и внутренний скролл. Ниже — по пунктам, от главного к второстепенному.

---

## 1. Главная находка: максимальная высота панели «перебивается» правилом из motion.css

Панель задумана как блок фиксированной высоты **с собственным скроллом**:

`vision/ui/static/css/blocks.css` (строка 12)
```css
.frame-analysis-panel {
    display: flex;
    flex-direction: column;
    gap: 5px;
    flex: 1 1 auto;
    min-height: 220px;
    max-height: 420px;   /* ← задуманный потолок */
    overflow: hidden;
    ...
}
```

Но в `vision/ui/static/css/motion.css` (строка 36) есть правило:
```css
#frame-analysis-panel.ui-collapse { max-height: 1600px; }
```

Специфичность у `#frame-analysis-panel.ui-collapse` — `(1,1,0)` (ид+класс), а у
`.frame-analysis-panel` — `(0,1,0)` (только класс). Ид-селектор **всегда побеждает**,
порядок подключения файлов роли не играет. Итог: `max-height: 420px` из blocks.css
никогда не срабатывает в развёрнутом состоянии — реальный потолок **1600px**.

### Что это ломает
- Вместо ограничения в 420px панель растёт до высоты всего своего контента
  (до 1600px). Правая колонка `.stats-panel` — `overflow: hidden` и жёстко
  привязана к высоте экрана (`html, body { height: 100vh; overflow: hidden }`).
- Внутренний кастомный скролл (`.fa-scroll-track` / `faSyncScroll`) рассчитан
  именно на то, что `.fa-cards` переполняется внутри панели 420px. Когда панель
  растягивается до 1600px, `.fa-cards` почти никогда не переполняется → дорожка
  скролла уходит в `is-idle` (скрывается) и **правила внизу списка становятся
  недоступны, если панель обрезается колонкой**.
- При большом числе правил панель занимает почти всю правую колонку и начинает
  «сжимать»/отжимать соседние блоки (Распределитель, Пороги, Ручное управление),
  которые `flex: 0 0 auto` и не умеют сжиматься — контент внизу колонки
  обрезается `overflow: hidden`.

**Причина:** рассинхрон двух ограничений высоты — авторское `max-height: 420px`
(с дизайном «блок + внутренний скролл») и анимационный `max-height: 1600px`
(«блок растёт на весь контент») конфликтуют, и побеждает то, что убивает замысел.

## 2. Пустое состояние при фильтре «СРАБОТАВШИЕ», когда все правила в норме

Фильтр по умолчанию — «СРАБОТАВШИЕ» (`frameAnalysisRulesFilter: 'triggered'`).
В `updateFrameAnalysisStatus` перед отрисовкой применяется фильтр:
```js
const visible = visibleFrameAnalysisRules(rules);
renderFrameAnalysisPanel(visible, ...);
```
`visibleFrameAnalysisRules` при фильтре `triggered` оставляет только
`part_absent / triggered / skipped` и **выбрасывает нормальные правила**.

Если все правила «в норме», в панель уходит **пустой массив** → рисуется заглушка
`fa-empty` («Ожидание результатов» / «НЕТ РЕЗУЛЬТАТОВ»), хотя анализ реально
прошёл и есть список нормальных правил. Панель выглядит «сломанной/пустой»,
хотя вердикт при этом может быть «ГОДНО».

**Причина:** фильтрация выполняется до рендера, поэтому отрисовщик не видит
«нормальных» правил и не может показать секцию «В НОРМЕ · N».

---

## 3. Кастомный скролл чувствителен к порядку разметки

`faSyncScroll` считает переполнение по `cards.scrollHeight - cards.clientHeight`
и рисует бегунок. Он вызывается в `requestAnimationFrame` после построения DOM —
если панель в этот момент была скрыта/не в layout (или работает эффект
`.ui-collapse` с `max-height`-анимацией), `clientHeight` может быть `0`, и дорожка
ошибочно скрывается (`is-idle`) или бегунок позиционируется неверно. Поверх
пункта 1 (скролл в принципе не нужен при высоте 1600px) это делает прокрутку
ненадёжной.

---

## 4. Контекст в шапке не обрезался (CSS)

`.fa-context` не имел ни одного CSS-правила. Длинный контекст вроде
«КОНТРОЛЬ +4 · ВНУТРЕННИЙ ВИД · КОРПУС #12» мог переноситься/распирать шапку
панели. Добавил `min-width: 0; overflow: hidden; text-overflow: ellipsis;
white-space: nowrap`, чтобы он аккуратно обрезался многоточием.

## 5. Клик по замеру «перепрыгивал» фильтр правил

`renderFrameAnalysisRules` (его вызывает `setMainCameraRun` при клике по замеру
прогона) был прямой ссылкой на `renderFrameAnalysisPanel` и отрисовывал **все**
правила без учёта активного фильтра «СРАБОТАВШИЕ»/«ВСЕ». При клике по замеру
панель на мгновение показывала полный список даже при включённом фильтре.
Заменил на обёртку, применяющую текущий фильтр.

## Замечание: fallback фильтра «СРАБОТАВШИЕ» (важное уточнение)

Проверка чистой логики показала: когда при фильтре «СРАБОТАВШИЕ» ни одно
правило не сработало и не пропущено, `triggeredRules` возвращает **полный**
список правил (`return filtered.length ? filtered : base`), а не пустой. Значит
обычный путь «все правила в норме» и так показывает панель корректно
(секция «В НОРМЕ · N», вердикт «ГОДНО»), без ложной заглушки. Пустой список
панель получает только когда правил нет вовсе (RUNNING без данных / камера без
правил) — тогда уместна заглушка «Ожидание результатов». Фикс «ВСЕ ПРАВИЛА В
НОРМЕ» остаётся как защита от гипотетического пустого `rules` с `totalRules > 0`.

## Исправлено дополнительно (коммиты b0c3e8f, edd2c85)

- **Реализован guard от избыточной пересборки.** Раньше при неизменных данных
  панель перестраивала DOM на каждом опросе (во время REVIEW ~10 раз),
  сбрасывая раскрытые «▸ Ещё N замеров» и позицию прокрутки. Теперь рендер
  повторяется только если поменялись данные, фильтр или прогон; маркеры
  последнего рендера обновляются в `updateFrameAnalysisStatus` и в
  обработчиках `setFrameAnalysisRulesFilter` / `setMainCameraRun`.

   сбрасывались на каждом опросе статуса.

## Хотите — исправлю
Самое вероятное «правильное» поведение по замыслу дизайна — панель 420px
с внутренним скроллом. Для этого нужно убрать/перебить `max-height: 1600px`
из motion.css (например, `#frame-analysis-panel.ui-collapse { max-height: 420px }`),
тогда кастомный скролл заработает как задумано.

при норме), — и я починю точную причину.
