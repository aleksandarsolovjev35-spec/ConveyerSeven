# ConveyerSeven — аудит и итоги работ

Дата: 2026-08-11.

Проведён обзор проекта: весь Python-код (~18 500 строк), JS/CSS/HTML,
конфигурационные файлы и документация, а также динамические проверки
(симуляция производственного цикла, фаззеры правил, smoke-тест UI-сервера,
compileall / pyflakes / node --check).

После обсуждения с автором все замечания разделены на два блока:
**осознанные проектные решения** (изменения не требуются) и **выполненные
правки** (чистка кода и документации).

---

## 1. Осознанные проектные решения автора — изменения не требуются

### 1.1 JOG — только центровка корпуса под камерой

JOG используется исключительно для небольшой центровки корпуса под камерой
(например, в паузе между шагами) и доступен в состояниях `IDLE` / `STOPPED` /
`PAUSED`. При таких малых перемещениях логические позиции деталей не
расходятся с физическими. Назначение JOG задокументировано в `README.md`.

### 1.2 FAULT — терминальное состояние (упрощённая безопасность)

Любая ошибка за время работы переводит линию в `FAULT`; выход — только
перезапуск системы. Это осознанная упрощённая модель безопасности: после
ошибки состояние механики неизвестно, и оно не «лечится» кнопкой. Поведение
сохранено как есть.

### 1.3 `stage_trace_time: 0.5` — визуализация этапов шага

Пауза перед каждым переходом фаз шага нужна, чтобы оператор видел этапы
(MOTION → SETTLE → CAPTURE → ANALYSIS → PUBLISH) по отдельности. На физику
линии она не влияет: пауза берётся, когда лента уже остановлена или ещё не
тронулась. Значение 0.5 с сохранено; документация приведена в соответствие.

### 1.4 `divisions_per_movement=2` — станции через два деления

Один шаг ленты (2 деления) доставляет корпус на следующую станцию
(+0 → +4 → +7). Это штатная геометрия линии, ошибкой не является.

### 1.5 Порог «пустого лотка» — подавление ложных срабатываний

Камера подтверждает наличие детали, только когда число `flatness`-находок
превышает `input_part_presence_false_positive_max_count` (по умолчанию 2).
Это необходимо для подавления случайных срабатываний моделей на пустом
лотке; модели отрабатывают надёжно. Принцип работы порога задокументирован
в `README.md`.

## 2. Выполненные правки: чистка кода и документации

Удалён мёртвый код, оставшийся от ранних версий, и устранены расхождения
комментариев с реальным поведением. Поведение системы не изменилось.

### 2.1 Удалена неиспользуемая цепочка `force_all_bad` / `force_bad`

Поле `ProductionCycle.force_all_bad` никогда не менялось с `False` и не имело
точек управления (ни API, ни UI), поэтому вся ветка «принудительный брак
всех деталей» была нерабочей. Удалены:

- `core/production_cycle.py` — поле `self.force_all_bad` и два аргумента
  `force_bad=self.force_all_bad` в вызовах инспектора;
- `inspection/inspector.py` — параметр `force_bad` из сигнатур
  `inspect_input_consensus`, `inspect_spider_consensus`, `_build_result` и
  ветка `defects = ["forced_bad"]`.

### 2.2 Удалена неиспользуемая функция `select_picture_run`

- `inspection/consensus.py` — удалена функция `select_picture_run`
  (общий помощник `_closest_metric` сохранён — его использует
  `describe_picture_run`);
- `inspection/inspector.py` — убран её неиспользуемый импорт.

### 2.3 `_evidence` → `_`

В `inspection/inspector.py` третье значение из `combine_rule_results`
(индекс прогона-свидетеля, при одиночном прогоне всегда 0) переименовано в
`_`.

### 2.4 Комментарии про `stage_trace_time` приведены в соответствие

- `core/step_stages.py` — комментарий над `STAGE_TRACE_SECONDS` переписан:
  пауза визуализации фаз в HMI; производственное значение приходит из
  `calibration.json`, константа — программный fallback;
- `config/calibration_loader.py` — комментарий в `OPTIONAL_DEFAULTS`
  переписан аналогично.

### 2.5 `setup.bat` — поддержка любой версии Python 3.11+

Скрипт больше не требует именно Python 3.11: перебираются
3.11 → 3.12 → 3.13 → любая доступная (`py -3`). README обновлён
(требование «Python 3.11+»).

### 2.6 Документация в `README.md`

- назначение и ограничения JOG (только центровка корпуса под камерой);
- принцип работы порога «пустого лотка» и когда его снижать;
- назначение `stage_trace_time` (визуализация фаз, не влияет на физику);
- требование Python 3.11+ и описание `setup.bat`.

## 5. Стык хост ↔ прошивка convey15 (2026-08-11, только Python)

Прошивка — фиксированный внешний компонент и не изменяется. Правки на
стороне хоста используют только её существующий командный набор.

### 5.1 `hardware/conveyor.py` — явная фиксация протокола остановки

Дефолты прошивки: межходовая пауза `G9` = 2000 мс (`WAIT=1` всё это время),
автопауза `G12` = 1. Хост ранее ни то, ни другое не отправлял, а
`_strict_stop_confirmed` требует `WAIT=0` — поэтому каждое подтверждение
остановки выжидало ~2 с мёртвого окна прошивки. `_set_params` теперь шлёт
`G12 S1` и `G9 S0`: автопауза-стоп сохранена, WAIT-окно исключено.

### 5.2 `hardware/conveyor.py` — fail-fast в `wait_stop`

- `lastErr` в прошивке липкий (команды сброса нет). Раньше при `lastErr≠0`
  хост 15 с ждал таймаут с неинформативным TimeoutError. Теперь — немедленный
  FAULT с указанием кода и необходимости перезапуска контроллера.
- Остановка принимается только при наличии доказательства хода (хотя бы один
  опрос с `MOV=1`, `POS≠0` или `TGT≠0`). Потерянная на линии команда `G3`
  раньше выглядела как мгновенная «чистая остановка» и молча разрывала
  соответствие деталь/позиция; теперь обнаруживается за
  `MOTION_EVIDENCE_TIMEOUT` (2.5 с) и переводит линию в FAULT.

### 5.3 `hardware/distributor.py` — abort homing при отказе хоста

Прошивка ищет концевик без ограничения пробега (до ~2 млн шагов). При
таймауте/отмене homing хост теперь шлёт `G25` обеим осям до выброса ошибки —
ось не остаётся в движении к упору после отказа запуска.

### 5.4 `main.py` — идентификация прошивки при старте

После открытия порта хост запрашивает `I6` и логирует имя/версию прошивки;
неопознанная прошивка — предупреждение на splash (не фатально: контроллер
уже идентифицирован форматом ответа на `I2`).

### 5.5 `calibration.json` — ограничение автономного пробега JOG

`jog_hold_steps`: 1 000 000 → 38 096 (2 деления, ~5 с хода). Dead-man
heartbeat живёт только на хосте (прошивка его не знает), поэтому длина
сегмента — единственная механическая граница пробега при смерти хост-процесса.
Ранее граница составляла ~52 деления (~50 с). На плавность удержания не
влияет: сегменты стыкуются воркером, а WAIT-окно на стыках убрано правкой 5.1.

## 6. Журналирование и автотесты (2026-08-11, только Python)

Две системные прорехи из обзора закрыты: «логирование» было 153 разрозненными
`print()` в консоль, а автотестов не было вовсе.

### 6.1 `core/app_logging.py` — новый модуль журналирования

- Файл сессии `logs/session_YYYYMMDD_HHMMSS.log` с ротацией (10 МБ × 5),
  миллисекундные таймстампы; в файл `DEBUG`, в консоль `INFO`. Каталог
  задаётся `LOG_DIR`, уровень консоли — `LOG_LEVEL`. `logs/` добавлен в
  `.gitignore`.
- `capture_prints()` — tee-перехват `stdout`/`stderr`: все оставшиеся
  `print(...)` (точечный прогресс загрузки и т.п.) попадают в файл под
  каналами `stdout`/`stderr`. Рекурсия «лог→tee→лог» исключена порядком
  инициализации: консольный обработчик держит исходный `stderr`.
- `install_excepthooks()` — необработанные исключения потоков и процесса
  пишутся в канал `crash` уровнем `CRITICAL`.
- `setup_logging()` идемпотентна; для тестов добавлены
  `_restore_print_streams()`/`_reset_for_tests()`.

### 6.2 Конверсия горячих путей print → get_logger

Переведены вызовы на критических путях производства: `core/production_cycle.py`
(32 вызова, канал `cycle`), `core/state_machine.py`, `core/step_stages.py`,
`core/live_preview.py`, `hardware/` (conveyor и так был без print; axis,
serial_transport, port_discovery, distributor), `vision/vision_cluster.py`
(пер-инференсные строки ушли в DEBUG, чтобы не гонять 18 записей на шаг),
`vision/camera_manager.py`, `inspection/`. Остальные `print` (main.py,
UI-сервер) сознательно оставлены под tee.
