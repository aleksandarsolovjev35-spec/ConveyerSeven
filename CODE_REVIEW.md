## 2. Сильные стороны

### 2.1. Фазовая модель шага и владение камерами
`core/step_stages.py` — лучший модуль проекта. Таблица допустимых переходов `_ALLOWED`,
исключение `StageSequenceError`, generation-счётчик против «поздних» кадров от прошлого шага.
Захват кадров возможен только в фазе `CAPTURE`, движение — только в `MOTION`; попытка снять
кадр на ходу невозможна не по договорённости, а структурно. Покрытие 83 %.

### 2.2. Fail-closed как сквозной принцип
- `CATEGORY_UNKNOWN` → трактуется как BAD, а не как GOOD.
- `REGION_MISSING_MARKERS` — отсутствие реперов не «пропускает» деталь.
- Любая ошибка шага → `_handle_fault`, терминальное состояние без авторетраев (осознанное
  решение, зафиксировано в `AUDIT.md`).
- `CameraManager._latch_failure` — «залипание» отказа камеры: восстановление только через
  явное `reopen_roles`, а не самопроизвольно между шагами.
- `_frame_error` проверяет форму, разрешение и near-black — чёрный кадр не уйдёт в inference.

Для линии контроля качества это правильный дефолт: цена ложного BAD несопоставима с ценой
пропущенного дефекта.

### 2.3. Работа с железом
`Conveyor.wait_stop` не верит одному флагу — требует свидетельств движения
(`MOTION_EVIDENCE_TIMEOUT = 2.5`). `Axis.verify_limit_config` / `verify_homed` проверяют
конфигурацию концевиков до первого движения. `Distributor` блокирует движение DIST2 при
открытом DIST1 (механическая коллизия невозможна программно). При shutdown и при FAULT
детали «в полёте» архивируются, а не теряются.

### 2.4. Управление жизненным циклом в `main.py`
Продуманная лестница таймаутов: `CYCLE_JOIN_TIMEOUT=15`, `INIT_JOIN_TIMEOUT=60`,
`GRACEFUL_EXIT_TIMEOUT=135`, `COMPRESS_TIMEOUT=60`. ESC один раз — штатный дренаж линии,
второй раз или FAULT — форсированный выход за 15 с. Порядок остановки соблюдён строго:
UI → архив → `live.stop()` → `cameras.release()` → `transport.close()`.
`_thresholds_apply` разрешает правку порогов только в IDLE/STOPPED и вне JOG, валидирует
неизвестные ключи и пересоздаёт `DecisionEngine` — конфиг не может «поехать» посреди партии.

### 2.5. Геометрия правил
`domain/defect_rules/omission_reference.py` — качественная численная работа: растеризация
масок, Theil–Sen вместо МНК, отбрасывание выбросов по 3×median, решение по доле инлайеров,
а не по худшей точке. Комментарии объясняют «почему», а не «что». `OmissionBoundaryMixin`
свёл оба omission-правила к 12 строкам каждое — образец того, как надо было сделать и с
contacts-правилами.

### 2.6. Конфигурация и валидация
`config/calibration_loader.py` строго валидирует `calibration.json`: обязательные и
опциональные ключи разделены, лишние ключи — ошибка, `type(x) is not int` (а не `isinstance`,
чтобы `True` не прошёл как int), проверка на конечность float. `PartArchive.validate_root`
реально пишет пробный файл с `fsync` и снимает `disk_usage` — не ограничивается `os.access`.
`can_reconfigure()` запрещает менять настройки архива после начала партии.

### 2.7. UI-сервер и стриминг
Двухуровневый кэш JPEG с инвалидацией по `_same_frames`/`_rules_equal`, автоподхват
`thresholds.json` по mtime только в безопасных состояниях. `routes_frames.py` — грамотный
MJPEG: версионирование кадров, отправка только при изменении версии, проверка
`request.is_disconnected()`, кодирование через `asyncio.to_thread` (event loop не блокируется).
Фронтенд поллит адаптивно: 60 мс в движении, 100 мс в RUNNING, 500 мс в покое.

### 2.8. Ленивые импорты пакетов
`hardware/__init__.py` и `inspection/__init__.py` используют `__getattr__` для отложенного
импорта — диагностические утилиты и тесты грузятся без `ultralytics`/`pyserial`. Именно
поэтому 121 тест проходит в окружении без тяжёлых зависимостей.

`ThresholdLoader.save_file` пишет `thresholds.json` напрямую — в отличие от

### 3.7. Диагностика с побочными эффектами
`diagnostic_analyze_selected_camera` (164 строки) вызывает приватный

изолировать в try-блок с собственным классом ошибок. Там же:
`Inspector._evaluate_part_presence` пересоздаёт объект правила на каждый кадр.

Это не прототип: система обращается со сбоями серьёзно (fail-closed по всем ветвям),
корректно завершает работу, не теряет детали при остановке и защищена типовым набором
проверок железа. Архитектура слоёв (`domain` / `core` / `hardware` / `vision`) выдержана,
ленивые импорты держат тесты быстрыми, `step_stages` и `omission_reference` — просто хороший
код.

уровня «свыше 300 строк», три копии одной карты правил, аналитический слой почти без тестов

блокирующим для эксплуатации, но каждое повышает стоимость следующей доработки. Пункты 1–4
плана убирают единственный реальный риск потери данных и фиксируют текущий уровень качества
малой кровью.

## 6. Выполненные исправления (блок «сейчас»)

### 6.1. Атомарная запись конфигурации

Создан общий модуль `domain/atomic_io.py`: `atomic_write_bytes` / `atomic_write_text` /
`atomic_write_json`. Схема одна для всех: временный файл **в каталоге назначения** →
`fsync` содержимого → `os.replace` → `fsync` каталога. При исключении временный файл
удаляется. `os.replace` атомарен только в пределах одной ФС — поэтому tmp не в `/tmp`.
Модуль лежит в `domain/`, так как этот пакет не импортирует ни `core`, ни `config`.

Переведены на общий модуль три места, писавшие файлы по-разному:

| Файл | Было | Стало |
|---|---|---|
| `domain/threshold_loader.py::save_file` | `open(path, "w")` + `write` | `atomic_write_text` |
| `config/archive_config.py::save_archive_config` | своя копия tmp+replace | `atomic_write_json` |
| `inspection/part_archive.py::_save_image` / `_write_json` | свои копии tmp+replace | `atomic_write_bytes` / `atomic_write_json` |

Смысл правки для линии: пороги правятся оператором прямо в смену. Обычный `open(..., "w")`
усекает файл сразу, а пишет содержимое потом — отключение питания между этими моментами
оставляло пустой `thresholds.json`, и линия не поднималась.

Тесты: `tests/test_atomic_io.py` (7 шт.), включая проверку, что целевой файл порогов
**не открывается** в режиме `"w"`. Тест проверен на регрессию: при возврате старой
реализации `save_file` он падает.

### 6.2. Диагностика больше не уводит линию в терминальный FAULT

Диагностика запускается оператором вручную в IDLE/STOPPED и не двигает ленту. Раньше любое
исключение внутри неё вызывало `_handle_fault` — линию приходилось поднимать перезапуском
процесса, даже если причиной была отключённая модель или опечатка в имени команды.

Введён `_handle_diagnostic_failure(kind, what, exc)`, который решает по факту состояния
оборудования, а не по факту исключения:

- **Прикладная ошибка** → статус диагностики `ERROR`, фаза `DIAGNOSTIC_ERROR`, предупреждение
  в лог; состояние линии сохраняется, проверку можно повторить.
- **Реальный отказ железа** → прежний `_handle_fault`. Признак отказа даёт
  `_hardware_failure_reason()`: ошибка `LivePreview` либо залипший отказ `CameraManager`.

Для этого у `CameraManager` появилось публичное свойство `failure_reason` — раньше
`_failed_reason` был приватным и снаружи нельзя было отличить «камера отвалилась» от
«кадр не разобрался». Это тот самый латч, из-за которого после отказа `capture_roles` и
`drain_buffers` навсегда блокируются, — теперь он читается явно.

Заменены четыре точки: `distributor_diagnostic`, `diagnostic_check_cameras`,
`diagnostic_check_vision_rules`, `diagnostic_analyze_selected_camera`. У
`distributor_diagnostic` дополнительно: проверка имени команды поднята **до** захвата
блокировки и до любого движения — неизвестная команда теперь не доходит до железа.

### 6.3. CI: pytest + ruff

- `ci/github-actions-ci.yml` — две задачи, `lint` (ruff) и `tests` (compileall + pytest),
  на push в любую ветку и на PR; `concurrency` отменяет устаревшие прогоны. Файл лежит в
  `ci/`, а не в `.github/workflows/`: у GitHub App нет разрешения `workflows`, и push с
  таким путём отклоняется. Включается одной командой — см. `ci/README.md`.
- `ruff.toml` — набор `E,W,F,I,B,UP` при `line-length = 120`. Стилистические правила,
  требующие массовой переработки живого кода (`BLE001` на 86 широких `except`, `S110`,
  `TRY004`), намеренно не включены: они разбираются отдельными задачами, а не блокируют
  каждый PR. В `ignore` с обоснованием: `E701/E702` (плотные таблицы команд распределителя),
  `UP042` (`State`/`StepStage` наследуют `(str, Enum)` — переход на `StrEnum` меняет
  `str()`/`format()`, а эти значения уходят в JSON статуса и сравниваются в UI).

  заменён на `opencv-python-headless`.

  локальный прогон и CI давали одинаковый результат.
