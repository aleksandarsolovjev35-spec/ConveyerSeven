## 2. Точная логика выбора «картинки» (кадра с разметкой)

Все вычисления — в `inspection/consensus.py`, применяются в `inspection/inspector.py` и `core/production_cycle.py`.

1. **Решающие правила:** при браке — только сработавшие правила; при годном — все правила.
2. **Решающая метрика правила:**
   - сработавшее правило → метрика, вышедшая за порог, с наименьшим расстоянием (наименее плохой дефект);
   - нормальное правило → метрика с наименьшим расстоянием в норме.
   - Ключ метрики = **(роль, key)** — метрики разных камер (SPIDER_LEFT/SPIDER_RIGHT) не смешиваются.
3. **Прогон внутри метрики:** приоритет у замера **в норме** с минимальным нормированным расстоянием `|value−limit| / max(1, |limit|)`; если все три замера метрики — брак, берётся замер с минимальным расстоянием; при равенстве — самый свежий прогон.
4. **Нет числовых порогов** → fallback на прежний evidence-прогон (по большинству голосов 2 из 3).
5. `select_picture_run` и `describe_picture_run` **всегда согласованы** (общий `_picture_choice`): строка «КАРТИНКА · ПРОГОН N: long_omission: SPIDER_LEFT · избыток 2 px (порог 3 px) — норма, ближе всего к порогу».

### Три замера порога (данные → UI)

- `inspection/consensus.py`: у каждого правила в `consensus.run_cards` — 3 карточки (по прогону) с метриками `{label, value, limit, ok, value_raw, limit_raw, key}`; `consensus.run_status` — статус области по прогонам.
- `core/rule_report.py`: `run_cards` + `run_status` попадают в строку отчёта; метрики получают **labels** из «Порогов правил» (`METRIC_PARAM_LABELS`); ручные `_label.*` применяются на сервере (`_apply_custom_threshold_labels`).
- UI (`rule-summary.js`/`diagnostics.js`): строка `роль · label | порог: N | замер1 замер2 замер3`; замер за порогом — красный, выбранный прогон — пунктирная рамка; слоты фиксированы номерами прогонов (пропуск — «—», без сдвига).

### Переключение кадров

- Backend хранит `run_frames` (3 набора кадров стадии) и `run_rule_results` (правила по прогонам, **до** majority-слияния) → кадр `/frame?run=N` рендерится с разметкой **своего** прогона.
- `/api/status` сообщает `frame_runs` (0 или 3); фронт включает переключение только при статичном анализе.
- Клик по кадру или клавиша N: `viewRun` 1→2→3→1; бейдж `АНАЛИЗ · ПРОГОН 2/3` / `СТОП-КАДР · ПРАВИЛА · ПРОГОН 1/3`; рамка замера в правой панели следует за прогоном.

## 6. Как запустить

```bash
# Демо без железа (Windows):
run_ui_only.bat

# Автотесты:
npm ci
npm run test:ui                     # JSDOM-матрица
.venv\Scripts\python.exe -m unittest discover -s tests   # Python
```

В демо: во время анализа клик по главному кадру или клавиша **N** переключают три кадра прогонов; бейдж и рамка замера следуют за прогоном; под правилами — три замера и полоса статусов «ОБЛАСТЬ НЕ ПОСТРОЕНА»; под вердиктом — «КАРТИНКА · ПРОГОН N: …».

## 7. Известные ограничения

1. **Ошибки окружения** (не связаны с правками): `test_prestart_diagnostics…`, `test_lifecycle…`, `test_hardware`, `test_distributor_calibration`, `test_startup_camera_recovery` — требуют реальных камер/моделей/серийного порта.
2. **Fail-closed правила без областей**: три замера отсутствуют физически (метрики `None`), поэтому в строках замеров — «—»; статус показывается полосой «ОБЛАСТЬ НЕ ПОСТРОЕНА».
3. **Сравнение расстояний** нормировано и сравнивается внутри одной (роль, метрика); между разными метриками расстояния не сравниваются.
4. Переключение кадров доступно только для **статичного анализа** (лента стоит); во время движения — поток.
